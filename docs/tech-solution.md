# 塔罗牌网站 · 技术方案

> 版本 v0.1 · 2026-10-01
> 配套文档：[产品设计文档](product-design.md)（要做什么、为什么）、[牌面素材来源记录](image-sources.md)（许可与出处）。

## 1. 技术选型

### 1.1 一句话结论

**Astro 静态优先 + 一个交互岛屿 + 零后端。**

全站约 80% 是可预渲染的静态内容，20% 是需要 JS 的抽牌流程。用岛屿架构，静态部分拿到 SSG 的 SEO 与加载速度，交互部分只挂一个客户端组件，不必为了一个抽牌按钮把整站变成 SPA。

### 1.2 选型总表

| 层 | 选择 | 说明 |
|---|---|---|
| 框架 | Astro | SSG 为主，抽牌流程做成一个岛 |
| 内容 | Content Collections + MDX + Zod | 78 张牌结构化校验，字段写错直接构建失败 |
| 交互 | 原生 TS + 状态机 | 主流程是线性状态机，手写 reducer 即可，不上重型状态库 |
| 样式 | Tailwind CSS | 移动端优先，迭代快 |
| 动画 | CSS / Web Animations API | 洗牌翻牌是一次性仪式动画，不值得引三方库 |
| 出图 | 客户端 Canvas + 字体子集内嵌 | 全站最大的技术风险点，见 4.3 |
| 存储 | sessionStorage，MVP 不上后端 | 与产品文档 4.2 节的会话状态设计一致 |
| 部署 | Cloudflare Pages 或 Vercel | 免费额度够；国内访问优先考虑 Cloudflare Pages |
| 测试 | Vitest + Playwright | 单测与端到端各一层 |

### 1.3 为什么是 Astro

- 78 张牌义页、教学页、愚者的旅程天然是静态内容。走 Content Collections + SSG，SEO 与首屏速度直接拿满，且完全不需要数据库。
- 只有抽牌流程需要 JS。岛屿架构对应「整站静态、单个组件上 JS」。
- 产品文档第 8 节的「首屏 2 秒内可交互」「单页推进不跳转」，Astro 加一个客户端组件基本是白送的。
- 78 个牌义页是主要的内容资产，静态路由与内容集合的支持比在 React 框架里手搓更直接。

### 1.4 什么时候该换成 Next.js

如果产品最终会长成「账号 + 收藏 + 社区 + 大模型个性化解读」的重应用，或者需要大量服务端逻辑，Next.js 会更顺手。但这几项已被明确划到验证之后，为可能不做的功能提前背复杂度不划算。真到那一步，Astro 也能挂 API、也能混进 React 岛，不至于推倒重来。

**判断节点**：阶段三的三项指标验证完之后再评估。

### 1.5 明确不做的事

- 不引入 SPA 框架接管整站
- MVP 不做 SSR、不做数据库
- 不为 V2 的大模型能力预留抽象层
- 不做账号与登录

## 2. 系统结构

### 2.1 目录结构

```text
tarot-site/
├── docs/
│   ├── product-design.md       # 产品方向、流程、决策
│   ├── tech-solution.md        # 本文件
│   └── image-sources.md        # 牌面素材来源与许可
├── public/
│   ├── img/cards/              # 78 张牌面 WebP（已完成）
│   ├── sw.js                   # Service Worker：「安装为应用」用
│   └── favicon.ico / icon-*.png
├── scripts/
│   ├── build-card-images.py    # 牌面转制，可复现
│   ├── make-icon.mjs           # 站点图标生成，零依赖
│   ├── serve.ps1               # 桌面入口用的本地静态服务（只用 PowerShell）
│   ├── create-shortcut.ps1     # 创建桌面与开始菜单快捷方式
│   └── smoke.mjs               # 构建产物的冒烟测试
├── src/
│   ├── content/
│   │   ├── cards/              # 78 个 MDX，阶段一产出
│   │   └── learn/              # 入门路径 7 课
│   ├── components/             # 岛屿组件：抽牌流程、分享卡片
│   ├── layouts/
│   ├── lib/                    # 状态机、解读拼接、禁忌拦截、随机抽牌
│   ├── pages/                  # 首页 / cards/[id] / learn / journey
│   └── scripts/read-app.ts     # 抽牌岛，全站唯一的客户端脚本
└── tests/                      # 校验与端到端测试
```

### 2.2 页面与路由

| 路由 | 类型 | 说明 |
|---|---|---|
| `/` | 静态 | 首页，入口与一句话说明 |
| `/read` | 静态外壳 + 一个岛 | 抽牌主流程，全部状态在同一个页面内 |
| `/cards` | 静态 | 78 张牌义索引 |
| `/cards/[id]` | 静态，78 条 | 牌义详情，SEO 与搜索流量的主要承接页 |
| `/learn` | 静态 | 入门教学路径 |
| `/journey` | 静态 + 轻交互 | 愚者的旅程，22 张大阿卡纳叙事 |

### 2.3 静态与交互的边界

边界只有一条：**需要用户输入和随机性的东西才上 JS。**

牌义详情、教学、索引页不挂任何客户端脚本；抽牌流程、分享出图挂一个岛；愚者的旅程只需要点击推进，用最轻的方式实现，能上 CSS 就不上组件。

## 3. 数据层

### 3.1 牌数据

每张牌一个 MDX 文件：短字段在 frontmatter，成段文案在正文。完整示例见产品文档 5.1 节，切分理由见 7.4 节。文件命名与 `public/img/cards/` 的图片一一对应。

### 3.2 构建期校验

用 Content Collections + Zod 定义 schema，把内容错误挡在构建阶段而不是运行时：

- frontmatter 字段的类型、枚举、必填项
- `image` 指向的文件是否真实存在
- 正文小节是否齐全（画面、象征、通用含义、这张牌不意味着什么、分场景含义、反思问题）
- 分场景含义是否覆盖全部一级问题分类

这一步的价值在阶段一就会体现：写到第 15 张牌时漏了一个小节，构建直接失败，而不是上线后才发现某个页面缺一块。

### 3.3 会话状态与随机性

```js
{
  questionType,        // 问题类型
  userNote,            // 用户补充（可选）
  confirmedQuestion,   // 确认后的问题
  cardId,              // 抽中的牌
  drawnAt,             // 抽牌时间戳
  answers: [],         // 反思问答的回答
  stage                // 当前步骤
}
```

状态存 sessionStorage，刷新后回到中断的那一步，不重新抽牌。

抽牌用 `crypto.getRandomValues`，**在翻牌动画开始前完成计算**，动画只是把已确定的结果呈现出来。时间戳一并记录，既用于当天的重抽限制，也为愿意深究的用户保留可追溯性。

### 3.4 解读生成：三层拼接

```
解读 = 牌面层（静态）+ 语境层（半静态）+ 个性化层（动态）
```

| 层 | 来源 | 工作量 |
|---|---|---|
| ① 牌面层 | 正文的「画面」+「象征」 | 78 条，逐张撰写 |
| ② 语境层 | 正文的「分场景含义」 | 大阿卡纳 22 × 5 = 110 条，逐条撰写 |
| ③ 个性化层 | 「反思问题」+ 建议句式池 | 组合生成 |

**小阿卡纳的语境层不逐条撰写**，改用生成规则：

```
语境解读 = 花色倾向（领域）× 数字阶段（1–10 的含义）× 牌义核心
```

四个花色各写一份领域倾向，数字 1–10 各写一份阶段含义，即可覆盖全部 56 张。280 条的工作量压缩到十几条规则，且口径一致。

个性化层只改变落地方式，不改变结论——这是产品文档第 2 节原则 2 的执行点。

## 4. 关键实现

### 4.1 抽牌主流程的状态机

主流程是一个线性状态机，步骤与产品文档 4.1 对应：

```
question-type → confirm → draw → core-reading → reflect(可跳过) → personal-reading → finish
```

要点：

- **回退**：步骤 1–3 可自由回退；回退到步骤 3 之前清空已抽的牌并明确提示
- **跳过**：`reflect` 可跳过，直接进入无个性化版本的第二层解读
- **重抽**：只在翻牌前允许返回重抽；翻牌后同一问题当天不可重抽
- **刷新恢复**：状态从 sessionStorage 还原，回到中断处
- **点击即前进**：选项点击直接进入下一步，不设提交按钮

状态机用纯函数实现，与 DOM 解耦，这样能用 Vitest 直接测状态迁移，不必起浏览器。

### 4.2 仪式动画

洗牌约 1.5 秒、翻牌约 0.8 秒，用 CSS / Web Animations API 实现。两条约束：

- **解读文本在洗牌动画开始时就在后台生成完毕**，动画结束即展示，用户感知为零等待
- **不使用假进度条**，需要等待时展示有实际含义的阶段文案

### 4.3 分享卡片出图

客户端 Canvas 绘制，流程：字体加载 → 布局计算 → 绘制 → `toBlob` 导出。

| 项目 | 说明 |
|---|---|
| 尺寸 | 竖版长图与方图两套，共用一份布局代码，只切换画布参数 |
| 内容 | 抽中的牌面、用户的问题、核心解读摘要、一句行动建议、站点标识 |
| 字体 | 子集化 woff2，目标 100KB 以内，只含常用汉字 + 拉丁字母 + 标点 |
| 降级 | 字体加载失败时回退系统字体栈，图上仍保留站点标识 |
| 验证 | iOS Safari 与微信内置浏览器各跑一遍真机 |

中文字体是这个功能唯一会真正翻车的地方，必须先做一个最小可用的导出 demo 验证，再往上堆设计。

**当前落地情况**：出图已经实现（`src/lib/share.ts`）。竖版长图 1080×1920 与方图
1080×1080 共用一份布局代码，只切换画布参数；牌面、问题、核心解读摘要、一句建议与站点标识都在图上。
**字体子集内嵌尚未做**，目前用系统字体栈渲染，并在 `document.fonts` 不可用时继续降级。
真机验证与 woff2 子集化仍是上线前的必做项，也是第 9 节列的头号风险。

### 4.4 内容禁忌的硬拦截

产品文档第 9 节的禁忌清单必须写进代码，作为硬性拦截，而不是靠撰稿人自觉：

- 拦截发生在**问题选择阶段**，不是用户抽完牌之后
- 生死与自伤类：终止解读并展示预先写好的关怀文案与专业求助渠道，不能临时生成
- 健康、数字、赌博、作奸犯科：不解读，转译为可回答的反思角度
- 拦截文案要友好，不能像报错

拦截规则与关怀文案放进独立模块，用单元测试覆盖每一类禁忌，保证全站口径一致。

## 5. 牌面素材管线

### 5.1 素材策略

MVP 采用 1909 年原始韦特牌的公版扫描件。理由：画面元素最丰富、用户认知成本最低、版权干净、无需自己画。完整论证见产品文档 7.3 节。

### 5.2 三个必须避开的坑

1. **不要用 1971 年美国游戏公司（U.S. Games Systems）的重新上色版**，那一版有独立的版权主张。判断特征：颜色更鲜艳饱和、线条有数字化修复痕迹。
2. **「Rider-Waite」「Rider-Waite-Smith」是注册商标**。图可以自由使用，但不能作为站名或品牌名，站内统一用「韦特体系」「经典塔罗」「公版韦特」。
3. **不从塔罗 App、博客或来源不明的打包仓库取图**，这类素材说不清许可，出问题时无法自证。

### 5.3 处理流程与当前状态

处理流程：统一画幅比 → 转 WebP → 保留来源与许可记录。逆位不单独出图，前端旋转 180° 即可。

| 项目 | 结果 |
|---|---|
| 素材 | 1909 年 "Pam-A" 版扫描件（Steve P. 清理修复），无损 PNG 1086×1810 |
| 获取途径 | `github.com/mixvlad/TarotCards` 仓库 `tarot/rider-waite/full-png/` |
| 站内文件 | `public/img/cards/*.webp`，78 张，800×1333，WebP 质量 82，合计约 18.8 MB |
| 命名 | `major-00` … `major-21`、`wands/cups/swords/pentacles-01` … `-14`，与牌数据 `id` 一一对应 |
| 转制脚本 | `scripts/build-card-images.py` |
| 许可记录 | [image-sources.md](image-sources.md) |
| 校验 | `tests/card-images.test.mjs`，Node 内置测试，零依赖 |

原始计划是从 Wikimedia Commons 直接下载。实际执行时该域名在当前网络环境下无法连通、本地代理也不可用，因此改从上述 GitHub 镜像仓库取回同一批 1909 年扫描件，来源与许可已完整记录。

### 5.4 备选路线

| 方向 | 代价 | 结论 |
|---|---|---|
| 更老的公版牌（马赛、维斯康蒂-斯福扎） | 视觉避开红海，但国内用户不认，牌义体系要跟着换 | 与现有韦特体系内容冲突，不采用 |
| 购买现代牌商业授权 | 费用与谈判成本高 | 对 MVP 不现实 |
| 约稿原创 78 张 | 成本高 | 等产品验证、有预算后再评估 |
| AI 生成 | 风格一致性难保证，模仿在世画师或既有牌组有风险 | 若要做，必须先定自己的视觉语言 |

## 6. 性能预算

78 张图是最大的性能风险点，从 MVP 阶段就要处理好。

| 指标 | 预算 |
|---|---|
| 首屏可交互时间 | 2 秒以内（移动端 4G） |
| 首屏 JS（gzip） | 只包含抽牌岛，静态页为零 |
| 首屏图片 | 不加载全部牌图，按需懒加载 + 骨架屏 |
| 单张牌面 | ≤ 512KB（当前最大约 400KB） |
| 牌面总体积 | ≤ 25MB（当前 18.8MB） |

后续优化方向：为列表页与分享图另出一套 400px 宽的缩略图，或改用 Astro 的 `src/assets` + `<Image>` 在构建期生成响应式变体。

## 7. 测试策略

| 层 | 工具 | 覆盖内容 |
|---|---|---|
| 单元 | Vitest | 状态机迁移、三层解读拼接、小阿卡纳生成规则、禁忌拦截、随机抽牌 |
| 内容 | 构建期校验 | Zod schema、正文小节完整性、图片路径存在性 |
| 素材与文档 | Node 内置测试 | 78 张牌齐全、命名合规、WebP 有效、尺寸体积达标（已落地） |
| 冒烟 | `pnpm verify` | 构建后逐个路由校验内容、数据文件、脚本挂载与静态页零 JS（已落地） |
| 端到端 | jsdom（Node 内置测试） | 用构建产物真实跑一遍抽牌流程：选问题 → 确认 → 选牌阵 → 洗牌与逐张翻牌 → 按牌位解读 → 反思问答 → 个性化解读 → 收尾（已落地） |

端到端这一层不引 Playwright：要跑真实浏览器就得下载浏览器内核，而这套流程里真正会出问题的部分是「脚本能不能跑起来、点下去有没有反应」——用 jsdom 加载构建产物、手动执行真正的客户端 bundle，就能覆盖。这一层是被事故逼出来的：子路径改写误伤了 JS 里的正则字面量，脚本语法报错、整页点不动，而当时所有单测与冒烟都是绿的。现在只要脚本跑不起来，这个用例会直接失败。

**内容即测试对象**：78 张牌的文案质量无法自动校验，但结构可以。所有内容结构错误都应该在构建期失败。

## 8. 部署

| 项目 | 方案 |
|---|---|
| 平台 | Cloudflare Pages（国内访问稍好）或 Vercel |

## 9. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 中文字体导出乱码 | 分享功能完全失效 | 先做最小导出 demo 验证，字体子集进仓库，真机验证 |
| 78 张图拖慢首屏 | 首屏预算失守 | 懒加载、骨架屏、后续补缩略图 |
| 内容量超出预期 | 阶段一拖长 | 小阿卡纳用生成规则，只逐条写大阿卡纳语境层 |
| 解读出现巴纳姆效应 | 产品可信度崩塌 | 产品文档 6.1 节的产出自检清单 + 语境层占比不低于 40% |
| 禁忌拦截漏判 | 合规风险 | 规则写进代码，单元测试逐类覆盖 |
| 商标用词渗进文案 | 法律风险 | 全站统一用「韦特体系」等描述性说法，评审时专门检查 |
