# 塔罗牌占卜网站 · 产品设计文档

> 版本 v0.2 · 覆盖 MVP 的整体方向、主要功能、核心流程与技术选型

---

## 1. 产品定位

**一句话**：一个面向所有人的塔罗解读工具，同时也是一条从零开始的塔罗入门路径。

**目标用户**

- 完全不了解塔罗、抱着好奇或怀疑心态进来的人
- 已经了解塔罗、对解读质量有判断力的人

这两类人必须同时被服务。第一类人决定网站能否传播，第二类人决定网站是否被认可。

**产品姿态**：反思工具，而非预测工具。

网站不告诉用户"会发生什么"，而是帮助用户看清"现在处于什么状态、有哪些被忽略的可能"。解读文案一律使用"这张牌提示你""可以想一想"这类句式，不使用"你将会""这代表必然"。

**差异化**：解释"为什么"。

市面上的塔罗产品大多只给结论。本站每张牌都解释画面里的元素为什么指向这个含义，并附带「这张牌不意味着什么」来破除常见误读。

---

## 2. 核心设计原则

以下五条贯穿全部功能设计，任何新功能都必须符合。

| # | 原则 | 含义 |
|---|---|---|
| 1 | 问题先于抽牌 | 用户必须带着已确认的问题抽牌，否则牌义失去解释锚点 |
| 2 | 抽牌结果独立于用户回答 | 结论在翻牌瞬间锁定，后续问答只改变落地方式，不改变结论 |
| 3 | 核心解读先于任何输入 | 用户走完抽牌即获得完整价值，问答是加深而非门槛 |
| 4 | 仪式感优先，规则用动画表达 | 洗牌、切牌、翻牌是不可省略的体验核心，但不写文字教程 |
| 5 | 语言不承诺预测 | 既是诚实姿态，也是合规前提 |
| 6 | 解读必须贴题 | 同一张牌在不同问题下必须给出不同解读，禁止通用文案 |

原则 2 是整套产品可信度的地基。一旦用户发现换个说法就能得到不同答案，产品就失去了意义。原则 6 同样关键——用户察觉"这段话换张牌也成立"的瞬间，信任就没了。具体执行标准见第 6 节。

## 3. 主要功能

### MVP 范围

**3.1 抽牌解读（主流程）**

产品的核心，其余功能都是它的支撑。详见第 4 节。

**3.2 牌义百科**

78 张牌的独立页面，静态内容，承接搜索流量并为解读页提供详情入口。

- 22 张大阿卡纳：完整版
- 56 张小阿卡纳：简化版（关键词 + 一句话含义），保证抽牌池完整

每张牌包含：牌名、元素与数字、关键词、画面描述、象征解释、通用含义、分场景含义、「这张牌不意味着什么」、反思问题。

**3.3 入门教学**

不写成百科索引，而是一条有顺序的学习路径：

塔罗是什么（含起源）→ 牌的结构（78 = 22 大阿卡纳 + 56 小阿卡纳）→ 花色与四元素 → 数字 1–10 → 宫廷牌 → 正逆位 → 牌阵。

**3.4「愚者的旅程」互动页**

把 22 张大阿卡纳串成愚者从出发到圆满的完整叙事，点击推进。这是新手理解大阿卡纳最有效的方式，也是站内最可能被分享的一页。

**3.5 解读保存与分享**

解读结果页在收尾处提供「保存图片」，生成一张包含完整解读的图片供用户保存到相册。这是此类产品最主要的自然增长渠道。

- 输出两种尺寸：竖版长图（适配微信、朋友圈、小红书）与方图（适配其他社交平台）
- 图片内容：抽中的牌面、用户的问题、核心解读摘要、一句行动建议、站点标识
- 全程在客户端生成，不上传服务器，不索取额外权限

### MVP 之外

三张牌阵、逆位开关、小阿卡纳补全、大模型个性化解读、账号与收藏、社区。这些留到主流程验证之后再评估。

## 4. 核心流程

### 4.1 主流程

| 步骤 | 用户动作 | 系统行为 | 耗时预算 |
|---|---|---|---|
| 0 | 进入首页 | 展示入口与一句话说明 | — |
| 1 | 选择问题类型 | 展示两级选项：8 个一级分类，每个分类下 3–5 个具体问法 | 20s |
| 2 | 确认问题 | 复述问题让用户确认，可选补一句自己的话 | 10s |
| 3 | 抽牌 | 洗牌 → 抽牌 → 翻牌（仅正位） | 5s |
| 4 | 阅读核心解读 | 立即展示：画面描述 → 象征含义 → 结合问题意味着什么 | 60s |
| 5 | 回答反思问题（可跳过） | 提出 1–2 个针对性问题，点击式选项 | 30s |
| 6 | 阅读个性化解读 | 第二层解读 + 一句可执行建议 | 40s |
| 7 | 收尾 | 保存解读图片 / 分享 / 查看完整牌义页 / 换个问题再抽 | — |

**目标：从进站到读完核心解读，控制在两分钟以内。**

### 4.1.1 问题类型选项表

采用两级结构。一级分类不超过 8 个，二级每个不超过 5 个，避免选项过多导致选择瘫痪。用户在二级选项上点击即前进，不需要额外的确认按钮。

**① 感情关系**

- 我现在的这段关系
- 单身与缘分
- 暧昧，说不清的状态
- 分手、复合与放下
- 这段关系还要不要继续

**② 职业与事业**

- 我目前工作的处境
- 求职与机会
- 要不要跳槽或转行
- 创业与副业
- 与同事、上级的相处

**③ 学业与方向**

- 现在的学业状态
- 考试与备考
- 专业、方向、路径的选择

**④ 财务与资源**

- 我目前的金钱状况
- 一笔具体的支出或投入
- 我与金钱的关系

**⑤ 一个具体决策**

- 二选一：A 还是 B
- 要不要做某件事
- 时机是否成熟

**⑥ 自我状态**

- 我最近的情绪
- 为什么我反复陷入同一个困境
- 我的优势与盲点
- 我想成为一个不一样的人

**⑦ 人际关系**

- 与朋友之间
- 与家人之间
- 我看不太懂的某个人

**⑧ 当下与整体**

- 今天的状态
- 这段时间的整体走向
- 有件事压在心里，但我说不清

此外，每一步都应常驻一个不占分类位置的出口：**「说不清，直接抽一张牌」**。这个出口对新手至关重要——不知道怎么提问的人，是本站最主要的目标用户。

### 4.1.2 提问的边界

拦截必须发生在问题选择的阶段，而不是用户抽完牌、读完解读之后才告诉他"这个问题不算数"。抽完再拒绝是最伤体验的做法。

- **可转译的问题**：界面引导用户换一个角度重新表述，照常进入解读
- **必须拒绝的问题**：不进入解读，友好说明并给出替代方向

两类问题的完整清单与处理方式见第 9 节。

### 4.2 状态与边界

每一步都必须明确定义前进之外的行为，否则用户会在中途卡死。

- **回退**：步骤 1–3 可自由回退。回退到步骤 3 之前会清空已抽的牌，需明确提示。
- **跳过**：步骤 5 可跳过，直接进入无个性化版本的第二层解读。
- **刷新恢复**：会话状态存入 sessionStorage，刷新后回到中断的那一步，不重新抽牌。
- **重抽**：仅允许在翻牌前返回重抽。翻牌后同一问题当天不可重抽，二次进入时提示"你已经为这个问题抽过这张牌了"。
- **放弃**：用户中途离开不报错，状态保留至会话结束。

### 4.3 抽牌规则的处理

洗牌、切牌、正逆位的规则本身在数字环境中不产生随机性差异，但它是整个体验的灵魂。

处理方式：用动画实现仪式感，不写文字教程；同时为好奇的用户提供「为什么要这样」的入口，链接到教学页。

## 5. 数据模型

内容与代码分离，全部数据结构化存储。

### 5.1 牌数据 `src/content/cards/*.mdx`

每张牌一个文件：代码需要读取和校验的短字段写在 frontmatter，成段的解读文字写在正文。这个切分方式见 7.4 节。

```mdx
---
id: major-00
name: 愚者
nameEn: The Fool
arcana: major          # major | minor
suit: null             # wands | cups | swords | pentacles
number: 0
element: air
keywords: [开始, 自由, 冒险, 天真]
image: /img/cards/major-00.webp
---

## 画面

一个年轻人站在悬崖边缘，脚边有只小狗……

## 象征

悬崖代表未知的边界，白色玫瑰代表纯粹……

## 通用含义

……

## 这张牌不意味着什么

愚者不代表愚蠢，也不代表鲁莽行事……

## 分场景含义

### 感情关系

……

### 职业与事业

……

## 反思问题

- 如果抛开所有顾虑，你最想迈出的那一步是什么？
```

切分规则：

- frontmatter 只放短字段：标识、牌名、牌组归属、元素、关键词、图片路径
- 成段叙述全部进正文，小节标题固定、顺序固定，模板按标题读取
- 「这张牌不意味着什么」与「反思问题」是结构的组成部分，不是可选补充
- 分场景含义的三级标题与问题类型一一对应，缺失的场景在构建期报错

### 5.2 解读生成：三层拼接

解读文本由三层组成，这是控制内容量与保证输出质量的关键。

```
解读 = 牌面层（静态）+ 语境层（半静态）+ 个性化层（动态）
```

| 层 | 来源 | 内容量 |
|---|---|---|
| ① 牌面层 | card.imagery + card.symbolism | 78 条，逐张撰写 |
| ② 语境层 | card.scenes[问题类型] | 大阿卡纳 22 × 5 = 110 条，逐条撰写 |
| ③ 个性化层 | card.reflection + 建议句式池 | 组合生成 |

**小阿卡纳的语境层不做逐条撰写**，改用生成规则：

```
语境解读 = 花色倾向（领域）× 数字阶段（1–10 的含义）× 牌义核心
```

四个花色的领域倾向、数字 1–10 的阶段含义各写一份即可覆盖全部 56 张。这样把 280 条的工作量压缩到十几条规则，且保证口径一致。

### 5.3 会话状态

```js
{
  questionType,        // 问题类型
  userNote,            // 用户补充（可选）
  confirmedQuestion,   // 确认后的问题
  cardId,              // 抽中的牌
  drawnAt,             // 抽牌时间戳
  answers: [],         // 反思问答的回答
  stage                // 当前步骤
}
```

**随机性**：使用 crypto.getRandomValues 生成抽牌结果，并在翻牌动画开始前完成计算。抽牌时间戳一并记录，既用于重抽限制，也为愿意深究的用户提供可追溯性。

## 6. 解读的个性化与语言规范

这一节是内容质量的核心约束，决定了产品能不能被信任。

### 6.1 个性化：同一张牌不能给所有人同一个答案

这是这类产品最容易失败的地方。如果「权杖二」对所有人都输出同一段话，用户很快会发现解读和自己的问题无关，产品的可信度会立刻崩塌。个性化必须由架构保证，而不是指望撰稿人自觉。

**① 问题决定方向。** 同一张牌在感情、职业、决策、自我状态等语境下指向的侧面完全不同。语境层必须逐个问题类型撰写，禁止复用同一段话。

**② 用户的原话要进入解读。** 如果用户在确认问题时补了自己的话，解读中应至少呼应一次他的原意，例如"你说你其实很怕失去现在的稳定——这张牌里那堵城墙，说的可能就是这个"。这是让用户感到被听见的最有效手段，实现成本却极低。

**③ 回答改变落地方式，不改变结论。** 反思问答的答案用于决定第二层解读的侧重方向和建议句式，不能改变牌的核心指向（见第 2 节原则 2）。

**产出自检清单**（每段解读写完后逐条自问）

- 这段话换成另一张牌还成立吗？成立则说明它没说出这张牌的特殊性。
- 这段话换到另一个问题类型下还成立吗？成立则说明它没有贴合语境。
- 这段话给任何人看都觉得对？那是巴纳姆效应，不是解读。
- 这段话里有没有用户可能反驳的具体断言？没有的话，它等于什么都没说。

**量化约束**：语境层文字占整段核心解读的比例不低于 40%。

### 6.2 语言：鲜活、具体、像人在说话

目标读者的跨度很大，从完全不信塔罗的人到熟悉塔罗的人。术语堆砌会把两类人都推开。

**要这样写**

- **先描述画面，再说含义。** 人是从画面进入一张牌的，不是从术语进入的。"画里的人站在城墙上望向远方，手里攥着一颗地球仪"比"权杖二象征远见与抉择"更有感染力。
- **用第二人称直接对话。** "你现在的位置其实并不差，你只是知道外面还有别的可能。"
- **承认不确定。** "这张牌在这里的含义有点模糊，可能是在说你还没准备好，也可能是说你其实准备好了，只是不愿意承认。"
- **用具体的生活场景代替抽象名词。** 不说"存在情感阻滞"，说"你想说的话到了嘴边，又咽了回去"。
- **允许温度和幽默。** 这是一次对话，不是一份报告。

**不要这样写**

- 术语堆砌："此牌属火元素，对应白羊座，象征意志力的初级形态。"
- 万能句式："保持开放的心态，一切都会好起来的。"
- 过度断言的预报："下个月你会遇到一个重要的人。"
- 神秘腔："命运之轮已然转动，黑暗中的力量正在苏醒。"
- 判决式语气："你这段关系没有希望了。"

**语气基准**：像一个懂塔罗但不装神弄鬼的朋友，坐在你对面，认真听完了你的问题，然后讲讲他从这张牌里看到了什么。

### 6.3 长度与排版

- 核心解读 200–350 字，太短显得敷衍，太长用户读不完
- 个性化解读 100–200 字
- 建议一到两句，必须具体到能执行
- 段落不超过三行，移动端一行控制在 15–25 字

## 7. 技术方案

先看形状：这个产品 **80% 是静态内容，20% 是一个交互岛屿**。78 张牌义页、教学页、愚者的旅程都是静态内容，需要 JS 的只有抽牌主流程。整套选型都建立在这一判断上。

### 7.1 框架选择：Astro

**决策**：Astro。

**理由**

- 78 张牌义页天然是静态内容，走 Content Collections + SSG，SEO 与首屏速度直接拿满，而且完全不需要数据库
- 只有抽牌流程需要 JS。岛屿架构正好是「整站静态、单个组件上 JS」，不必为了一个抽牌按钮把整站变成 SPA
- 第 8 节的「首屏 2 秒内可交互」「单页推进不跳转」这两条要求，Astro 加一个客户端组件基本是白送的

**什么时候该换成 Next.js**

如果这东西最终会长成「账号 + 收藏 + 社区 + 大模型个性化解读」的重应用，或者需要大量服务端逻辑，Next.js 更顺手。但这几项已经被明确划到验证之后，为了可能不做的功能提前背上复杂度不划算。真到那一步，Astro 也能挂 API、也能混进 React 岛，不至于推倒重来。

**明确不做的事**

- 不引入 SPA 框架接管整站
- MVP 不做 SSR
- 不为 V2 的大模型能力预留抽象层

### 7.2 完整选型

| 层 | 选择 | 说明 |
|---|---|---|
| 框架 | Astro | SSG 为主，抽牌流程做成一个岛 |
| 内容 | Content Collections + MDX + Zod | 78 张牌结构化校验，字段写错直接构建失败 |
| 交互 | 原生 TS + 状态机 | 主流程是 8 步线性状态机，XState 或手写 reducer 都行，不上重型状态库 |
| 样式 | Tailwind CSS | 移动端优先，迭代快 |
| 动画 | CSS / Web Animations API | 洗牌翻牌是一次性的仪式动画，不值得引三方库 |
| 出图 | 客户端 Canvas + 字体子集内嵌 | 最大的技术风险点，见 7.5 |
| 存储 | sessionStorage，MVP 不上后端 | 与 4.2 节的会话状态设计一致 |
| 部署 | Cloudflare Pages 或 Vercel | 免费额度够；Pages 在国内访问稍好一点 |
| 测试 | Vitest + Playwright | 单测与端到端各一层，够用 |

### 7.3 牌面素材策略

**决策**：MVP 使用 1909 年原始韦特牌的公版扫描件，统一转 WebP。

**为什么是这一套**

- **画面元素最丰富**：本产品的差异化是解释画面元素为什么指向某个含义，Smith 的牌每张都塞满了可解读的细节，别的牌未必经得起这么拆
- **用户认知成本最低**：国内用户搜到的塔罗牌几乎都是这套，牌义页的辨识度最高
- **版权最干净**：1909 年出版，作者 1951 年去世，在美国与中国均已进入公有领域，可商用、可修改、无需付费
- **不需要自己画**：78 张原创的成本对 MVP 不现实

**必须避开的三个坑**

- **不要用 1971 年美国游戏公司（U.S. Games Systems）的重新上色版**。那一版有独立的版权主张，不属于公有领域。判断特征：颜色更鲜艳饱和、线条有数字化修复痕迹。网上随手存的「高清韦特牌」多半是这版
- **「Rider-Waite」「Rider-Waite-Smith」是注册商标**，图和名字是两回事。图可以自由使用，但不得作为站名或品牌名，站内统一用「韦特体系」「经典塔罗」「公版韦特」
- **不直接从塔罗 App、博客或来源不明的打包仓库取图**，这类素材说不清许可，出问题时无法自证

**拿到图之后统一做三件事**

统一画幅比（移动端用竖版）、转 WebP 并生成多尺寸、留存许可来源记录。逆位不单独出图，前端旋转 180° 即可。

**当前落地情况**

已采用 1909 年 "Pam-A" 印刷版的扫描件（由 Steve P. 清理修复），转制为 800×1333、WebP 质量 82 的一套图，放在 `public/img/cards/`，78 张齐全。来源、许可与命名规则的完整记录见 `docs/image-sources.md`，转制脚本见 `scripts/build-card-images.py`。

**备选方案（未采用，仅作记录）**

| 方向 | 代价 | 结论 |
|---|---|---|
| 更老的公版牌（马赛、维斯康蒂-斯福扎） | 视觉上完全避开红海，但国内用户不认，牌义体系也要跟着换 | 与现有以韦特为基础的内容冲突，不采用 |
| 购买现代牌的商业授权 | 费用与谈判成本高 | 对 MVP 不现实 |
| 约稿原创 78 张 | 成本高 | 等产品验证、有预算后再评估 |
| AI 生成 | 78 张风格一致性难保证，模仿在世画师或既有牌组有风险 | 若要做，必须先定自己的视觉语言，不得照着韦特改 |

### 7.4 卡片内容的存储格式

**决策**：代码要读取的短字段放 frontmatter，成段文案放 MDX 正文，每张牌一个文件 `src/content/cards/<id>.mdx`。

**理由**：`keywords`、`suit`、`image` 这类字段需要被代码读取和校验，适合结构化；而「画面」「象征」「通用含义」「分场景含义」都是成段的叙述文字，塞进 YAML 既不能换行排版，Git diff 也难读。阶段一要连写 22 张大阿卡纳，格式选错会让整个撰写过程非常难受。

**约束**

- 用 Content Collections + Zod 定义 schema，字段缺失或类型错误在构建期直接失败
- frontmatter 只放短字段；正文按固定小节、固定顺序撰写，模板按标题读取
- 「这张牌不意味着什么」和「反思问题」属于内容结构，缺失同样要在构建期报错
- 完整的文件示例见 5.1 节

### 7.5 分享卡片出图方案

**决策**：客户端 Canvas 手绘，内嵌子集化的中文字体（woff2）。

**理由**：Satori、html-to-image 这类「DOM 转图」方案更适合服务端渲染，与 3.5 节「全程在客户端生成、不上传服务器」的约定冲突。移动端 Canvas 不保证有可用中文字体，不内嵌字体，导出图片必然乱码或空白。

**约束**

- 字体子集只包含实际用到的字符（常用汉字 + 拉丁字母 + 标点），目标 100KB 以内，子集化脚本进仓库
- 两种尺寸共用一份布局代码，只切换画布参数，输出竖版长图与方图
- 上线前必须在真机验证：iOS Safari 与微信内置浏览器各跑一遍
- 字体加载失败时降级到系统字体栈，并保证图上仍有站点标识

### 7.6 后端与埋点

**决策**：MVP 保持零后端，流程状态只存 sessionStorage；阶段三要观察的三项指标用轻量埋点采集。

**理由**：抽牌、解读生成、出图全都能在客户端完成；账号、收藏、社区都在 MVP 之外，提前引入后端只有运维与合规成本，没有当期收益。

**约束**

- 埋点只记录匿名事件（流程完成率、牌义页点击率、二次回访），不采集用户输入的问题内容
- 埋点脚本异步加载，不进入首屏关键路径
- V2 若引入大模型个性化解读，再单独评估服务端方案，现在不预留抽象层

### 7.7 解读生成

MVP 用模板引擎做三层拼接（见 5.2），稳定、可控、零成本、无幻觉。大模型是 V2 的可选升级，届时站内已有足够语料做约束。

### 7.8 部署

Cloudflare Pages 或 Vercel，连 Git 仓库自动构建，免费额度足够。国内访问优先考虑 Cloudflare Pages。

## 8. 流畅度

流畅度在这个产品里不只是性能问题，它直接决定仪式感能否成立。

**等待要有意义，但不能真的卡。** 解读文本在洗牌动画开始时就在后台生成完毕，动画结束即展示，用户感知为零等待。动画时长约为洗牌 1.5 秒、翻牌 0.8 秒。

**不使用假进度条。** 需要等待时展示有实际含义的阶段文案（如"正在为你展开牌面"），而非装饰性的百分比。

**单页推进，不做整页跳转。** 流程各步骤在同一页面内切换，状态由路由或锚点承载，避免白屏与滚动位置丢失。

**点击即前进。** 选项点击后直接进入下一步，不设"提交"按钮，减少每一次多余点击。

**移动端优先。** 目标用户大量来自手机，牌面图片、字号与触控区域一律按移动端设计，再向上适配。

**首屏性能预算**：首屏可交互时间控制在 2 秒以内，首屏不加载全部牌图。

**恢复能力**：任一环节刷新、返回、断网重连后都能回到原位，不丢状态、不重复抽牌。

## 9. 内容禁忌与合规

### 9.1 绝对禁忌

以下五类问题在产品的任何环节都不回答，包括主流程、每日一牌、牌义页示例和分享文案。这不是尺度问题，是底线。

| 禁忌 | 具体表现 | 处理方式 |
|---|---|---|
| **生死** | 寿命、何时去世、亲人安危、自杀与自伤相关 | 立即终止解读，展示关怀提示与专业求助渠道 |
| **健康** | 疾病诊断、用药、治疗方案、怀孕与胎儿情况 | 不解读，转译为"我可以怎样照顾自己"的反思角度 |
| **数字** | 预测彩票、抽奖号码、赌博结果、具体日期与金额 | 不解读，说明这不在塔罗能回应的范围内 |
| **赌博** | 赌局输赢、投注建议、牌局走向 | 不解读，引导向"我为什么想赌"的自我觉察 |
| **作奸犯科** | 违法犯罪的方法、规避后果、伤害他人 | 立即终止，不作任何回应 |

其中生死与自伤相关的处理要格外谨慎：不只是拒绝回答，而应当给出明确的关怀文案与专业求助渠道。这块文案必须提前写好、经过推敲，不能临时生成。

### 9.2 需要转译的方向

| 用户想问的 | 界面转译为 |
|---|---|
| 我得了什么病 / 要不要吃这个药 | 面对现在的身体状况，我可以怎样照顾自己 |
| 他到底爱不爱我 / 他在想什么 | 在这段关系里，我真正在意的是什么 |
| 这笔投资会不会赚 | 面对这个决定，我该关注哪些自己可控的因素 |

理由有三层：健康与法律问题需要专业人士而非占卜；第三方的内心无法被观测，任何断言都是编造；投资建议涉及真实的经济损失。

### 9.3 产品定位表述

定位统一为「文化、娱乐与自我觉察工具」。

禁用表述：预测命运、保证准确、改运、化解、转运、破解、必灵。

推荐表述：自我探索、心理投射、文化解读、反思、参考。

这不是单纯的过审考量。目标用户中包含不相信塔罗的人，语言上的克制恰恰是赢得他们信任的方式。

### 9.4 落地要求

- 禁忌规则要写进解读生成逻辑，作为硬性拦截，而不是只靠撰稿人自觉
- 拦截文案必须友好，不能像报错。用户被拒绝时的体验，往往决定他会不会再回来
- 全站统一适用同一套规则，包括牌义页示例、分享图片和每日一牌

## 10. 里程碑

**阶段一 · 内容先行（不写代码）**

完成 22 张大阿卡纳的完整内容，以及小阿卡纳的生成规则（花色倾向 + 数字阶段）。同时把第 6 节的个性化与语言规范、第 9 节的禁忌清单落成可执行的撰写标准，包括拦截话术和关怀文案。

先写内容再写代码，是因为这批内容既是网站的骨架，也是判断"模板生成够不够用"的唯一依据。写完 22 张之后，对流程该长什么样的判断会和现在完全不同。

**阶段二 · MVP**

首页 + 抽牌主流程 + 每日一牌 + 78 张牌义页 + 入门教学 + 愚者的旅程 + 保存与分享图片。

**阶段三 · 验证后迭代**

依据三项指标决定投入方向：用户能否不看说明走完流程、读完解读后是否点进牌义页、是否会回来抽第二次。
