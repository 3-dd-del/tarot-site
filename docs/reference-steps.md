# 参考步骤

> 版本 v0.3 · 2026-10-01
> 用途：把塔罗牌网站跑起来、在桌面留一个双击就能打开的入口；第 7 节记录下一步的牌阵改造方案。
> 相关文档：[技术方案](tech-solution.md)、[产品设计文档](product-design.md)。

## 0. 前提

站点已经建好（Astro 静态站 + 一个抽牌岛），78 张牌面与牌数据都在仓库里。
所以现在只剩两件事：**跑起来**，然后**在桌面留一个入口**。

---

## 1. 建站与运行（Astro）

项目结构已经是 Astro 的标准结构，不需要再执行 `npm create astro@latest`。常用命令在仓库根目录执行：

```bash
pnpm install     # 安装依赖
pnpm dev         # 开发预览，通常跑在 http://localhost:4321
pnpm build       # 生成静态站点到 dist/
pnpm preview     # 预览构建产物
pnpm verify      # 构建 + 冒烟测试（路由、数据、脚本挂载）
```

抽牌流程需要 JS，其余页面在构建期就已经渲染成静态 HTML。

---

## 2. 选择在哪里打开

先决定网页从哪里来，桌面入口才有东西可指向。

### 方式 A：部署到公网（推荐，尚未执行）

好处是手机、别的电脑都能打开，桌面快捷方式指向一个固定网址，不依赖本机有没有开服务。

1. 把代码推到 GitHub（已在做）
2. 去 Cloudflare Pages 或 Vercel 注册，关联这个仓库
3. 构建命令填 `pnpm build`，输出目录填 `dist`
4. 得到形如 `https://tarot-site.pages.dev` 的网址

### 方式 B：只在本地跑（当前采用）

好处是不用部署、不依赖网络；坏处是每次使用前都要先把服务启动起来。
下面的第 3 节把这一步压缩成了一次双击。

---

## 3. 创建桌面快捷方式

### 3.1 一键脚本（当前采用）

先构建一次，再运行创建脚本：

```bash
pnpm build
powershell -ExecutionPolicy Bypass -File scripts\create-shortcut.ps1
```

会在桌面和开始菜单各生成一个「塔罗牌」图标，双击之后：

1. `启动塔罗牌.bat` 调起 `scripts/serve.ps1`
2. 脚本用 Windows 自带的 PowerShell 起一个本地静态服务（默认 4321 端口）
3. 自动打开浏览器指向 `http://localhost:4321/`

两个细节：**这条路径不需要安装 Node**，服务只用到 PowerShell；重复双击不会报端口占用，脚本检测到服务已经在跑就只打开浏览器。

关闭那个命令行窗口，本地服务就停了。

### 3.2 安装成应用（体验最好）

部署到公网之后（方式 A），在 Edge 或 Chrome 里打开该网址：

1. 地址栏右侧有「安装」图标；找不到就进菜单 → 应用 → 安装此站点为应用
2. 装完会自动在桌面与开始菜单生成图标
3. 打开时是独立窗口，没有地址栏，看起来与桌面软件一致

项目已经准备好 `public/site.webmanifest`、`public/sw.js` 与 192/512 图标，所以这条路径不需要额外改代码。

### 3.3 手动指向网址

桌面空白处右键 → 新建 → 快捷方式 → 位置填网址 → 名称写「塔罗牌」。
双击即可打开，但它会开成一个普通浏览器标签页。

---

## 4. 换图标

图标不依赖任何图像工具，由脚本直接生成：

```bash
node scripts/make-icon.mjs
```

会写出 `public/favicon.svg`、`public/favicon.ico`（16/32/48/64/128/256 六种尺寸）、`public/apple-touch-icon.png`、`public/icon-192.png`、`public/icon-512.png`，以及桌面快捷方式用的 `assets/tarot.ico`。

要换图标时改这个脚本里的图形函数即可；如果只想给现有快捷方式换一个 `.ico`，右键快捷方式 → 属性 → 更改图标 → 浏览。

---

## 5. 三种方式对比

| 方式 | 依赖本机服务 | 图标来源 | 适用场景 |
|---|---|---|---|
| 一键脚本 + 本地服务 | 是 | `assets/tarot.ico` | 已构建、只想在本机用（当前采用） |
| 安装为应用 | 否 | 站点 favicon | 已部署，想要接近桌面软件的体验 |
| 快捷方式指向网址 | 否 | 手动设置 | 已部署，只要一个桌面入口 |

---

## 6. 最短路径

**现在：`pnpm build` → 运行 `scripts\create-shortcut.ps1` → 双击桌面的「塔罗牌」。**

**以后部署完：用 Edge / Chrome 的「安装此站点为应用」生成桌面图标，本地的 `启动塔罗牌.bat` 就可以不用了。**

## 7. 下一步改造：牌阵与多张牌的顺序（尚未实施）

> 本节是方案，不是现状。代码落地之后，把内容并回[技术方案](tech-solution.md)与[产品设计文档](product-design.md)。

### 7.1 先分清「牌位」和「顺序」

真实玩法里这是两件事：

- **顺序**：这是第几张抽出来的。有的流派会读它，第一张是起因，第二张是发展
- **牌位**：这张牌落在牌阵的哪个格子。位置本身带含义（阻碍、建议、对方的立场）

两种实现路子：

| 做法 | 谁决定位置 | 体感 |
|---|---|---|
| 顺序决定位置 | 抽第一张自动落到第一位 | 快，但用户是旁观者 |
| 位置决定顺序 | 用户点哪个格子，牌从牌堆顶依次给 | 更接近真实玩法（推荐） |

推荐第二种，同时保留顺序作为可读信号（翻牌时显示「第 1 张 / 共 3 张」）。这样两件事都在，用户也不会困惑。

### 7.2 改造清单

| 文件 | 改什么 |

| `src/lib/machine.ts` | Session 用 `cards` 数组替换 `cardId`；重抽的 key 从「问题」改成「问题 + 牌阵」；新增 spread、reveal 阶段 |
| `src/lib/spreads.ts` | 新增。牌阵定义：位置、坐标、位置提示语、位置之间的关系 |
| `src/lib/reading.ts` | 从单张拼接改成「按牌位逐张 + 总述」 |
| `src/lib/relations.ts` | 新增。关系层：元素配比、大阿卡纳占比、数字连续性 |
| `src/lib/reflect.ts` | 反思问题可以按位置补一题（可选） |
| `src/scripts/read-app.ts` | 逐张翻牌流程与牌阵布局 |
| `src/pages/read.astro` | 新增「选牌阵」与「翻牌」两个步骤的容器 |

### 7.3 数据模型与状态机

```ts
interface DrawnCard {
  positionId: string    // 'present' | 'obstacle' | 'advice'
  cardId: string
  order: number         // 第几张被翻开
  reversed: boolean     // 为逆位预留
}
// Session 里用 cards: DrawnCard[] 取代 cardId: string | null
```

流程从：

```text
question → confirm → draw → core → reflect → personal → finish
```

变成：

```text
question → spread → confirm → shuffle → reveal(逐张) → reading → reflect → personal → finish
```

两个要点：

- `reveal` 阶段每翻一张只给一句「这个位置在问什么」，**不要提前给整段解读**，否则用户翻到第二张就不翻了
- 解读按**牌位顺序**展开，不是抽牌顺序，最后再补一段「这几张牌放在一起在说什么」

### 7.4 牌阵定义

新建 `src/lib/spreads.ts`：

```ts
interface Spread {
  id: string
  name: string
  cardCount: number
  questionTypes?: CategoryId[]   // 适合哪几类问题
  positions: { id: string; label: string; prompt: string; x: number; y: number }[]
  relations: { from: string; to: string; label: string }[]
}
```

先做三个就够：

| 牌阵 | 张数 | 位置 |
|---|---|---|
| 一张牌 | 1 | 当下、需要看见什么 |
| 三张牌 | 3 | 现状—阻碍—建议（另有「过去—现在—未来」变体） |
| 二选一 | 5 | 现状 / A 的走向 / A 的代价 / B 的走向 / B 的代价 |

凯尔特十字最后做，它的问题不是难，是信息过载。

牌阵不要一上来让用户选：**按问题类型自动推荐一个，旁边留「换一个牌阵」**，匹配关系写进 `questionTypes`。

### 7.5 解读结构：三层变五层

```text
① 牌面层   这张牌本身（画面 + 象征）        已有
② 牌位层   它出现在哪个位置                  新增，10–20 条
③ 语境层   结合你的问题                      已有
④ 关系层   和别的牌怎么呼应                  新增，规则生成
⑤ 个性化层 呼应你的原话 + 建议               已有
```

**这里有个内容陷阱。** 如果把位置语义写成结论（「过去发生了什么」「你的阻碍是 X」），同一张牌在三个位置的文案就要各写一份：22 × 8 × 3 = 528 条，不可接受。

正确的切法是**牌位层只写「提问角度」，不写结论**：

- 过去位：「这件事的起点在哪里」
- 阻碍位：「是什么让这件事停住了」
- 建议位：「如果把注意力放在一个地方，放哪里」

这样牌位层只有十几条，语境层保持 176 条不变，新增内容量很小。

### 7.6 关系层用可计算的信号

三张牌摆在一起时，能算出来的信号有：四元素配比、大阿卡纳占比、数字的连续与断层、同花色扎堆。这些可以直接推文案，例如「三张里有两张是宝剑，说明这件事主要发生在想法和沟通层面，而不是现实条件上」。

反过来，**「这两张牌在互相呼应」这类话不要凭感觉生成**。用户一旦察觉是套话，整个牌阵的可信度就没了——和产品设计文档第 6 节那条「语境层占比不低于 40%」是同一个道理。

### 7.7 出图、测试与文档

- 出图：竖版长图适合三张牌竖排；方图只放牌阵缩略 + 一句结论
- 新增四条测试：
  1. 牌阵定义完整：位置数、坐标不重叠、每个位置都能取到解读
  2. 同一张牌在不同位置输出不同的话
  3. **翻牌顺序不改变抽到的牌**（公平性，必须做）
  4. 多张牌的长图不溢出
- 文档：产品设计文档第 3、4、5 节与技术方案第 2、3、4 节要一起改

### 7.8 其他手感建议

按「和真实玩法的差距」从大到小：

1. **让手参与。** 现在点一下就全自动，差距最大的一环。把 78 张摊成扇形或几摞牌堆，用户自己点、自己拖、自己切。
2. **洗牌要有节奏。** 真实洗牌是「哗啦—哗啦—哗啦」三段，不是一次匀速动画。
3. **切牌让用户自己切。** 对结果没用，但这是仪式本体。
4. **翻牌要有延迟。** 轻触 → 牌微微抬起 → 翻过来 → 停半秒再出文字。太快反而廉价。
5. **牌阵的形状本身是信息。** 三张横排和凯尔特十字，视觉上就该不一样。
6. **读完不要自动跳。** 把停顿还给用户。
7. **保留「我也不确定」。** 三张牌里总有一张是含混的，硬给结论反而假。
8. **顺序要显示出来。** 「第 1 张 / 共 3 张」，让第一张牌有重量。
9. **重抽规则收紧。** 同一问题 + 同一牌阵，当天不重抽。
10. **给本地历史。** localStorage 存最近几次抽牌，不做账号、不上传。

### 7.9 建议的落地顺序

- **第一批**：三张牌阵（现状—阻碍—建议）+ 逐张翻牌 + 牌位层 + 关系层。做完体感就完全变了
- **第二批**：扇形摊牌、手动切牌、二选一牌阵、牌阵推荐
- **第三批**：逆位开关、凯尔特十字、本地历史

### 7.10 开工前的一个提醒

产品设计文档第 3 节把「三张牌阵、逆位开关」明确划在 MVP 之外，理由是先用单张牌验证三件事：用户能不能不看说明走完、读完会不会点进牌义页、会不会回来抽第二次。

现在加牌阵，等于把验证推到更后面。这不代表不该做——牌阵确实是「更像塔罗」的关键一步。但建议先看一眼那三件事的数据，哪怕只找五个人试一次单张流程；如果「走完流程」本来就有卡点，加牌阵只会让卡点更长。
